# 全项目代码审查与重构 - 技术设计

## Context

### 背景

项目经过多轮迭代后,代码库积累了大量技术债务:

1. **样式系统混乱**: 5种样式方法混用,CSS变量重复定义,硬编码颜色50+处
2. **配置管理分散**: 前端、主进程、后端各自管理配置,缺乏同步机制
3. **Legacy代码未清理**: 新旧代码共存,迁移未完成
4. **API结构不清晰**: Legacy和v1 API并存,缺乏版本控制
5. **文档组织混乱**: 100+个文档散落各处,缺乏索引

### 约束

- **向后兼容**: 阶段性迁移,避免一次性破坏所有功能
- **数据安全**: 配置迁移不能丢失用户数据
- **性能要求**: 重构不能降低性能
- **测试覆盖**: 重构前后测试覆盖率不能下降
- **开发效率**: 重构期间不能阻塞新功能开发

### 利益相关者

- **开发团队**: 需要清晰的架构和规范
- **用户**: 需要稳定的功能和一致的体验
- **运维团队**: 需要简化的配置和部署流程

## Goals / Non-Goals

### Goals

1. **消除代码冗余**: 删除重复代码,统一实现方式
2. **统一样式系统**: 建立清晰的样式规范,确保一致性
3. **集中配置管理**: 统一配置架构,实现前后端同步
4. **完成Legacy迁移**: 删除所有Legacy代码,统一使用适配器
5. **规范API结构**: 清理Legacy API,建立版本控制机制
6. **整理文档**: 创建文档索引,归档历史文档
7. **提升测试覆盖**: 前端>70%,后端>85%

### Non-Goals

1. **不重写核心功能**: 重构不改变现有功能逻辑
2. **不引入新框架**: 使用现有技术栈,避免学习成本
3. **不优化性能**: 性能优化是后续任务,本次聚焦代码质量
4. **不添加新功能**: 重构期间不开发新功能

## Decisions

### 决策1: 样式系统统一方案

**选择**: 使用CSS变量 + Tailwind + 统一的样式工具函数

**理由**:
- CSS变量提供主题切换能力
- Tailwind提供快速开发能力
- 工具函数封装复杂样式逻辑(如玻璃效果)

**替代方案**:
- ❌ 纯CSS-in-JS: 性能开销大,不符合现有架构
- ❌ 纯Tailwind: 无法实现动态主题切换
- ❌ 纯CSS: 开发效率低,难以维护

**实施**:
```typescript
// 1. CSS变量定义 (index.css)
:root {
  --color-primary: 59 130 246;  // RGB格式,便于透明度调整
  --color-background: 255 255 255;
  --spacing-4: 1rem;
}

// 2. Tailwind使用
<div className="bg-[rgb(var(--color-primary))] p-4">

// 3. 工具函数
import { getGlassClass } from '@/utils/styleUtils';
<div className={getGlassClass('medium')}>
```

### 决策2: 配置管理架构

**选择**: 后端统一配置源 + 前端缓存 + 实时同步

**架构图**:
```
┌─────────────┐      HTTP API      ┌─────────────┐
│   Frontend  │ ←─────────────────→ │   Backend   │
│ ConfigStore │   GET /v1/config   │  Config API │
│  (Zustand)  │   PUT /v1/config   │ (FastAPI)   │
└─────────────┘                     └─────────────┘
      ↓                                    ↓
  localStorage                        .env + DB
  (缓存/离线)                        (持久化)
```

**理由**:
- 后端作为配置源,确保一致性
- 前端缓存提升性能,支持离线
- 实时同步确保配置变更及时生效

**替代方案**:
- ❌ 前端独立管理: 无法与后端同步,配置不一致
- ❌ 完全依赖后端: 离线无法使用,性能差
- ❌ 配置文件同步: 复杂度高,容易出错

**实施**:
```typescript
// 前端 ConfigStore
export const useConfigStore = create<ConfigStore>((set, get) => ({
  config: null,
  
  loadConfig: async () => {
    try {
      // 1. 尝试从后端加载
      const response = await fetch('/v1/config');
      const config = await response.json();
      
      // 2. 缓存到localStorage
      localStorage.setItem('config', JSON.stringify(config));
      
      set({ config });
    } catch (error) {
      // 3. 降级到本地缓存
      const cached = localStorage.getItem('config');
      if (cached) {
        set({ config: JSON.parse(cached) });
      }
    }
  },
  
  updateConfig: async (updates) => {
    // 1. 更新到后端
    await fetch('/v1/config', {
      method: 'PUT',
      body: JSON.stringify(updates)
    });
    
    // 2. 更新本地状态
    set({ config: { ...get().config, ...updates } });
    
    // 3. 更新缓存
    localStorage.setItem('config', JSON.stringify(get().config));
  }
}));
```

### 决策3: Legacy代码迁移策略

**选择**: 适配器模式 + 渐进式迁移 + 最终删除

**迁移路径**:
```
阶段1: 创建适配器
├── ai-adapter.ts (✅ 已完成)
├── vision-adapter.ts (✅ 已完成)
├── voice-adapter.ts (✅ 已完成)
├── patient-adapter.ts (⏳ 待实现)
├── agent-adapter.ts (⏳ 待完善)
└── config-adapter.ts (⏳ 待实现)

阶段2: 更新引用
├── 全局搜索 legacy 导入
├── 替换为 adapter 导入
└── 验证功能正常

阶段3: 删除Legacy
├── 删除 src/services/legacy/
├── 删除相关脚本
└── 清理文档
```

**理由**:
- 适配器模式支持新旧实现切换,降低风险
- 渐进式迁移避免一次性破坏
- 最终删除消除技术债务

**替代方案**:
- ❌ 一次性重写: 风险高,容易引入bug
- ❌ 永久保留Legacy: 维护成本高,代码混乱
- ❌ 分支开发: 合并困难,容易冲突

### 决策4: API版本控制机制

**选择**: URL路径版本控制 + 废弃警告 + 迁移指南

**版本策略**:
```
v1 (当前稳定版)
├── /v1/ai/*
├── /v1/vision/*
├── /v1/voice/*
├── /v1/agent/*
└── /v1/config/*

v2 (未来版本)
├── /v2/ai/*  (改进的响应格式)
├── /v2/vision/*  (支持批量处理)
└── ...

Legacy (废弃)
├── /api/ai_chat  (→ /v1/ai/chat)
├── /api/model-config  (→ /v1/config/models)
└── ...
```

**废弃流程**:
1. **标记废弃**: 在响应头添加 `X-API-Deprecated: true`
2. **警告日志**: 记录使用废弃API的调用
3. **迁移指南**: 提供详细的迁移文档
4. **宽限期**: 保留3个月后删除
5. **最终删除**: 返回410 Gone状态码

**理由**:
- URL路径版本控制清晰直观
- 废弃警告给用户迁移时间
- 迁移指南降低迁移成本

**替代方案**:
- ❌ Header版本控制: 不直观,容易遗漏
- ❌ 查询参数版本控制: URL不清晰
- ❌ 直接删除: 破坏性太强,用户体验差

## Risks / Trade-offs

### 风险1: 配置迁移数据丢失

**风险等级**: 高

**影响**: 用户配置丢失,需要重新设置

**缓解措施**:
1. **迁移前备份**: 自动备份现有配置到 `config.backup.json`
2. **迁移脚本**: 提供配置迁移脚本,自动转换格式
3. **验证机制**: 迁移后验证配置完整性
4. **回滚方案**: 迁移失败时自动回滚到备份

**回滚计划**:
```bash
# 1. 检测迁移失败
if [ $? -ne 0 ]; then
  # 2. 恢复备份
  cp config.backup.json config.json
  # 3. 重启服务
  systemctl restart desktop-ai-assistant
fi
```

### 风险2: 样式破坏

**风险等级**: 中

**影响**: 部分组件样式显示异常

**缓解措施**:
1. **渐进式迁移**: 一次迁移一个组件,逐步验证
2. **视觉回归测试**: 使用Playwright截图对比
3. **主题测试**: 测试所有主题(玻璃、浅色、深色)
4. **浏览器测试**: 测试主流浏览器兼容性

**测试清单**:
- [ ] 主窗口样式正常
- [ ] 对话组件样式正常
- [ ] 设置面板样式正常
- [ ] 玻璃效果正常
- [ ] 深色模式正常
- [ ] 主题切换无闪烁

### 风险3: API不兼容

**风险等级**: 中

**影响**: 前端调用失败,功能不可用

**缓解措施**:
1. **完成remove-legacy-api**: 确保前端已迁移到v1 API
2. **API测试**: 所有v1 API有完整测试覆盖
3. **版本检查**: 前端检查后端API版本
4. **降级处理**: API调用失败时降级到本地实现

**版本检查**:
```typescript
// 前端检查后端版本
const checkAPIVersion = async () => {
  const response = await fetch('/v1/version');
  const { version } = await response.json();
  
  if (version < '2.0.0') {
    console.warn('Backend API version too old, some features may not work');
  }
};
```

### 风险4: 测试覆盖不足

**风险等级**: 中

**影响**: 重构引入bug,未被测试发现

**缓解措施**:
1. **先写测试**: 重构前先添加测试,确保行为不变
2. **代码审查**: 所有变更都要经过代码审查
3. **CI/CD检查**: 测试覆盖率低于目标时构建失败
4. **手动测试**: 关键功能进行手动测试

**测试优先级**:
1. P0: 核心功能(AI对话、患者提取、配置管理)
2. P1: 常用功能(语音输入、截图、主题切换)
3. P2: 辅助功能(快捷键、通知、日志)

## Migration Plan

### 阶段1: 准备阶段 (1天)

1. **创建备份**
   ```bash
   # 备份配置
   cp -r config config.backup
   cp src/renderer/App.css src/renderer/App.css.backup
   cp src/renderer/index.css src/renderer/index.css.backup
   
   # 备份数据库(如果有)
   pg_dump medical_ai > backup.sql
   ```

2. **创建迁移分支**
   ```bash
   git checkout -b refactor/codebase-cleanup
   ```

3. **通知团队**
   - 发送邮件通知重构计划
   - 暂停新功能开发
   - 协调代码审查资源

### 阶段2: 执行阶段 (5周)

按照tasks.md中的任务清单逐步执行,每个阶段完成后:

1. **自测**: 开发者本地测试
2. **代码审查**: 提交PR,团队审查
3. **CI测试**: 自动化测试通过
4. **手动测试**: QA团队验证
5. **合并主分支**: 通过后合并

### 阶段3: 验证阶段 (1周)

1. **功能测试**: 验证所有功能正常
2. **性能测试**: 确保性能未下降
3. **兼容性测试**: 测试不同环境
4. **用户验收**: 内部用户试用

### 阶段4: 部署阶段

1. **灰度发布**: 先发布给10%用户
2. **监控指标**: 监控错误率、性能
3. **收集反馈**: 收集用户反馈
4. **全量发布**: 无问题后全量发布

### 回滚方案

如果发现严重问题:

1. **立即回滚**
   ```bash
   git revert <commit-hash>
   git push origin main
   ```

2. **恢复配置**
   ```bash
   cp -r config.backup/* config/
   ```

3. **通知用户**: 发送通知说明回滚原因

4. **问题修复**: 在分支中修复问题,重新测试
