# 全项目代码审查与重构提案

## Why

经过多轮迭代开发后,项目代码库积累了大量技术债务,严重影响开发效率和代码质量:

### 核心问题

1. **代码冗余严重**
   - 前端样式系统存在23个一致性问题,CSS变量在多处重复定义且值不一致
   - 配置管理在前端(configStore)、主进程(config.ts)、后端(config.py)三处独立实现,缺乏统一管理
   - AI服务、视觉服务、语音服务等在legacy和adapters中存在双重实现

2. **架构混乱**
   - Legacy代码与新适配器代码共存,但迁移未完成(7个服务中仅3个完成)
   - 后端API路由混乱:同时存在`/api/*`(legacy)和`/v1/*`(新版),缺乏清晰的废弃计划
   - 前端服务层职责不清:adapters、legacy、直接API调用三种模式混用

3. **配置管理混乱**
   - 前端配置存储在electron-store,后端配置在.env文件,两者不同步
   - 配置项重复定义:如AI模型配置在前端、后端、config/models.json三处都有
   - 缺乏统一的配置验证和类型安全

4. **样式系统不一致**
   - 5种不同的样式实现方法混用(CSS变量、Tailwind、内联样式、CSS类、主题配置)
   - 玻璃效果实现不统一,存在废弃的`dark:glass-dark`类
   - 50+处硬编码颜色值,主题切换不完整

5. **文件组织混乱**
   - 大量文档散落在根目录(23个.md文件)和docs目录(100+个文档)
   - 测试文件组织不清晰,部分测试在tests/,部分在backend-service/tests/
   - 临时文件和备份文件未清理(如App.css.backup、.env copy)

### 业务影响

- **开发效率低**: 新功能开发需要在多处修改配置,容易遗漏
- **维护困难**: 代码重复导致bug修复需要多处同步
- **新人上手难**: 架构不清晰,文档混乱,学习曲线陡峭
- **质量风险**: 样式不一致影响用户体验,配置不同步导致运行时错误

## What Changes

### 阶段1: 代码清理与整理 (P0 - 紧急)

#### 1.1 清理冗余文件
- **删除备份文件**: `App.css.backup`、`index.css.backup`、`.env copy`
- **整理文档**: 将根目录的23个.md文件归档到docs/archive/或合并到主文档
- **清理临时文件**: 删除或归档测试报告、分析报告等临时文档

#### 1.2 统一样式系统
- **合并CSS变量定义**: 删除`App.css`中的重复定义,统一使用`index.css`
- **移除废弃类**: 清理所有`dark:glass-dark`使用,统一使用`.glass`
- **审计硬编码颜色**: 替换50+处硬编码颜色为CSS变量或Tailwind类
- **创建样式规范**: 文档化样式使用规范,添加ESLint规则强制执行

#### 1.3 完成Legacy迁移
- **完成剩余适配器**: 实现patient-adapter、agent-adapter、config-adapter
- **删除Legacy代码**: 迁移完成后删除`src/services/legacy/`目录
- **更新导入引用**: 全局替换legacy导入为adapter导入

### 阶段2: 配置管理统一 (P1 - 重要)

#### 2.1 统一配置架构
- **创建配置中心**: 后端提供统一的配置API(`/v1/config/*`)
- **前端配置同步**: 前端configStore从后端加载配置,而非独立管理
- **配置验证**: 使用Zod(前端)和Pydantic(后端)进行类型安全验证

#### 2.2 简化配置文件
- **合并重复配置**: 将`config/models.json`、`config/scenarios.json`合并到后端配置
- **环境变量规范**: 统一.env文件格式,添加详细注释和示例
- **配置文档**: 创建配置项完整文档,说明每个配置的作用和默认值

### 阶段3: 后端API清理 (P1 - 重要)

#### 3.1 完成Legacy API移除
- **完成remove-legacy-api变更**: 确保所有前端调用已迁移到v1 API
- **删除Legacy路由**: 删除`/api/ai_chat.py`、`/api/model_config.py`等legacy路由
- **更新API文档**: 更新README_API.md,移除legacy端点文档

#### 3.2 规范API结构
- **统一响应格式**: 所有API使用`APIResponse`包装
- **错误处理标准化**: 统一错误码和错误消息格式
- **添加API版本控制**: 为未来v2 API预留扩展空间

### 阶段4: 代码结构优化 (P2 - 一般)

#### 4.1 前端组件重构
- **拆分大组件**: 将超过300行的组件拆分为子组件
- **提取公共逻辑**: 创建自定义Hooks提取重复逻辑
- **统一状态管理**: 规范Zustand store使用,避免prop drilling

#### 4.2 后端服务重构
- **服务层解耦**: 将业务逻辑从API路由中提取到services层
- **依赖注入**: 使用FastAPI的依赖注入管理服务实例
- **错误处理**: 统一异常处理和日志记录

#### 4.3 测试覆盖提升
- **前端测试**: 为关键组件和Hooks添加单元测试
- **后端测试**: 确保所有v1 API有对应的测试用例
- **E2E测试**: 添加关键用户流程的端到端测试

### 阶段5: 文档和工具 (P2 - 一般)

#### 5.1 文档整理
- **创建文档索引**: 在docs/README.md中创建分类索引
- **归档历史文档**: 将过时的分析报告移到docs/archive/
- **更新开发指南**: 更新QUICK_START.md、TESTING_GUIDE.md等

#### 5.2 开发工具
- **代码审计脚本**: 扩展audit-frontend-styles.sh为全面的代码审计工具
- **自动化检查**: 添加pre-commit hooks检查代码规范
- **CI/CD优化**: 优化测试和构建流程

- **API路由**: 清理legacy端点,统一v1 API

#### 后端

- `backend-service/app/api/v1/` - 添加config API

#### 文档
- 根目录 - 清理23个.md文件
- `docs/` - 创建索引,归档历史文档

#### 配置
- `config/models.json` - 合并到后端配置
- `config/scenarios.json` - 合并到后端配置
- `.env.example` - 更新和规范

### 破坏性变更

- **BREAKING**: 删除`src/services/legacy/`目录,所有导入必须更新
- **BREAKING**: 删除legacy API端点(`/api/ai_chat`等)
- **BREAKING**: 前端配置加载方式变更,需要后端配置API支持
- **BREAKING**: CSS变量定义位置变更,可能影响自定义样式

### 迁移路径

1. **阶段1完成前**: 保持向后兼容,新旧代码共存
2. **阶段1完成后**: 删除legacy代码,更新所有导入
3. **阶段2完成后**: 前端配置从后端加载,需要后端先部署
4. **阶段3完成后**: Legacy API完全移除,前端必须使用v1 API

### 风险评估

| 风险 | 等级 | 缓解措施 |
|------|------|---------|
| 样式破坏 | 中 | 全面测试,保留备份,渐进式迁移 |
| 配置丢失 | 高 | 配置迁移脚本,数据备份,回滚计划 |
| API不兼容 | 中 | 完成remove-legacy-api变更后再删除 |
| 测试覆盖不足 | 中 | 先添加测试,再重构代码 |
| 文档过时 | 低 | 同步更新文档,代码审查检查 |
